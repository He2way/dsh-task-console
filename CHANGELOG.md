# Changelog / 变更记录

All notable changes to `dsh-task-console` are recorded here. Versions follow `package.json`.

本文件记录 `dsh-task-console` 的版本变更，版本号与 `package.json` 一致。

## v0.24.1

- **Fixed: creating controls from a conversation failed on the canvas / 修复：对话在画布上新建控件失败** — a reply that wrote its controls **with the kind as the key** instead of the documented `kind` field (`{ "stats": [ … ] }`, `{ "trend": { … } }`, `{ "note": "…" }`, and even `{ "heading": "标题", "text": "正文" }`) landed on the plane as `未支持的控件：unknown` boxes: five of them in the reported case, and nothing usable was created. The control parser now recovers the shape a conversation actually wrote:
  - **Kind as the key** — `{ "stats": [ … ] }` / `{ "trend": { … } }` / `{ "note": "…" }` / `{ "chips": ["a"] }` becomes the real control (arrays land in the field that kind expects: `items`, `rows`, `values`), and `{ "heading": "标题", "text": "正文" }` keeps the longer `text` as its body instead of the key's value. A single item written without the wrapper (`{ "stats": { "label": "上证", "value": "3,215" } }`) is wrapped too.
  - **Kind names in Chinese and synonyms** — `表格`, `计数器`, `折线图`, `待办`, `标题`, `代码块`, `网页应用`, `图片` … plus English synonyms (`metrics`, `todo`, `sparkline`, `iframe`, …) all map to the canonical kinds, matched case- and separator-insensitively.
  - **Kind-less blocks are recognised from their fields** — `{ until: … }` → countdown, `{ src: … }` → image, `{ url: … }` → embed, `{ values: [1,2,3] }` → trend, `{ columns, rows }` → table, `{ rows: [[k,v]] }` → kv, `{ label, value }` → stats, `{ text }` → text.
  - **Nothing vanishes silently** — a control this client still cannot build is skipped **and named** in the summary the conversation reads (`已应用：新增控件 2 · 跳过 1（看板）`), instead of either a dead error box or a bare `没有改动`. The `unknown` placeholder keeps the name it was authored with through every sanitize round-trip, and its snapshot now also carries flat lists, so a stored placeholder can still be upgraded once the client knows that shape. The canvas prompt states the rule with a full example ("把控件名写在 kind 字段里，不要把控件名当键").
  - **Fixed the bug underneath the report** — `trend` never read its own canonical `items` back: any trend control that went through a **second** sanitize (which is what the canvas `add` op, the instance adopt and the explode path all do) was silently dropped, so a `{"op":"add","kind":"trend"}` op could never create anything. Every kind now survives a sanitize round-trip, and a test asserts exactly that for all 19 kinds.
  - **Regression tests** — the reply transcribed from the reported canvas (eight kind-as-key blocks plus two `add` ops) is a fixture in `smoke.mjs`: it must parse into three ops with nothing dropped and build a five…eight-control card plus the two bare controls, with no `unknown` block anywhere. `npm run verify:embed` feeds the same shape through the main conversation in Chromium and asserts the plane shows real controls (`kinds=trend`, `unsupported=0`) with a drawn trend chart.
- **修复：对话在画布上新建控件失败**：如果回复把控件名**当成键**写（`{ "stats": [ … ] }`、`{ "trend": { … } }`、`{ "note": "…" }`，甚至 `{ "heading": "标题", "text": "正文" }`）而不是写文档规定的 `kind` 字段，画布上就会出现一摞 `未支持的控件：unknown` 方框（用户这次是 5 个），什么控件都建不出来。现在控件解析器会还原对话真正写出的形状：**控件名当键**（数组会落到该控件对应的字段：`items` / `rows` / `values`），`{ "heading": "标题", "text": "正文" }` 会保留更长的 `text` 作为正文；没写 `items` 包装的单个条目（`{ "stats": { "label": "上证", "value": "3,215" } }`）会自动包上；**中文名与同义词**（表格 / 计数器 / 折线图 / 待办 / 标题 / 代码块 / 网页应用 / 图片，以及 metrics、todo、sparkline、iframe 等英文同义词）都能映射到规范控件名，匹配时忽略大小写与分隔符；**完全没写控件名时按字段判断**（`until` → 倒计时、`src` → 图片、`url` → 网页应用、`values` → 趋势、`columns`+`rows` → 表格、`rows` → 键值、`label`+`value` → 统计、`text` → 文本）。**不再静默丢弃**：仍然建不出来的控件会被跳过并**在摘要里点名**（`已应用：新增控件 2 · 跳过 1（看板）`），而不是留下一个死掉的错误框或一句"没有改动"；`unknown` 占位块在每次消毒往返后都保留它被写出来时的名字，快照里也开始携带扁平列表，因此已存的占位块在客户端认识该形状后仍能升级。画布提示词里明确写出规则并给出完整示例（"把控件名写在 kind 字段里，不要把控件名当键"）。**顺带修掉报告背后的老 bug**：`trend` 从不读取它自己的规范字段 `items`，于是任何经过**第二次**消毒的趋势控件（画布 `add` 操作、实例收养、展开控件都会走第二次）都会被静默丢掉——`{"op":"add","kind":"trend"}` 因此永远建不出东西；现在 19 种控件都能通过"消毒两次结果不变"的测试。回归测试：把报告里那块画布上真实出现过的回复（8 个"控件名当键"的块 + 2 个 `add` 操作）作为 `smoke.mjs` 的固定用例——必须解析成 3 个操作、零丢弃，建出含 8 个控件的卡片与两个裸控件，且不出现任何 `unknown` 块；`npm run verify:embed` 在 Chromium 里把同样形状的回复从主对话送进去，断言画布上是真正的控件（`kinds=trend`、`unsupported=0`）并且趋势图真的画了出来。

## v0.24.0

- **The canvas hosts any plugin, not only cards and controls / 画布可以承载任何插件，不局限于卡片与控件** — a conversation (or the `🧩 插件` picker) can now put **another plugin's own UI** onto a canvas. The item is not a card kind: the plugin's client bundle is materialized from the boot manifest, its embed entry mounts into a host node the item owns, and the item behaves like everything else on the plane (drag, resize, `✎` / `💬` / `⛶` / `⧉` / `📥` / `🗑`, `▢` for the bare look).
  - **Two new `[canvas]` ops** — `{ "op": "addPlugin", "id": "dsh-plugin-tpt-chronicle", "title": "工作时序", "height": 420, "bare": true?, "x": 数字?, "y": 数字? }` and `{ "op": "rebuild", "id": "已有项 id" }` — parsed, validated (`sanitizePluginRef`) and reported like the rest (`新增插件 1 · 重建插件 1`); unusable references are skipped and counted. The canvas prompt lists the plugins the boot manifest knows (✓ marking the ones that already mounted once) and teaches both ops, so "把工作时序插件放到画布上" just works from either conversation box. `applyCanvasSpec` accepts the raw op shape (`id` / `pluginId` / `plugin` as a string) as well as the parsed one, for programmatic callers.
  - **Embedding contract** — the plugin publishes `globalThis.__DSH_<ID WITHOUT dsh-plugin->__.mountEmbedded(host, api)` (the same convention the built-in 工作时序 card already relies on: `dsh-plugin-tpt-chronicle` → `__DSH_TPT_CHRONICLE__`); `api` hands it `render` (a dedicated React root), `dark` and `onStatus`, which the item's live badge shows (待挂载 / 加载中… / 已挂载 / 未挂载). `mount(host, api)` and a plain function are accepted too, and an item may name its entry explicitly.
  - **One load, many mounts** — the bundle is fetched once per session and every item of that plugin mounts into its own host (no iframe, no second React copy, the plugin keeps its own DOM, styles and API access); `⟳` in the item header — or the `rebuild` op — sets a new revision, which re-materializes the bundle and remounts. Revisions now always move forward (`nextPluginRevision`), so two rebuilds inside the same millisecond can no longer leave the old UI in place.
  - **It degrades loudly** — a plugin with no embed entry, an id missing from the boot manifest or a bundle that fails to load shows a `插件无法显示：…` panel naming the expected global and a one-line example, instead of an empty box. The `🧩 插件` picker also lists the dynamic plugins reported by the plugin-management port (`◇` rows), which have no bundle URL of their own.
  - **Both conversations drive it** — the canvas' own chat box could already do this, and now so can the **main conversation**: the chat-row watcher applies a `[canvas]` block found in any reply (the same watcher that already authors cards from `[taskcard]`), targeting the canvas the block names (`"canvas": "名字或 id"`, created when it does not exist yet) or the active canvas, and the board shows a clickable notice — `画布「发布画布」已应用：新增插件 1` — that opens exactly that canvas. A reply may carry both protocols at once; the canvas block is applied first. Nothing else about the protocol changes: same ops, same validation, same summary.
  - **Fixed while testing this** — two teardown bugs that only surfaced when canvases were switched with plugin items (or any embedded app) on the plane: (1) a hosted plugin root was unmounted *and* its host node cleared by hand, but `root.unmount()` may defer its DOM deletion (React defers a `flushSync` issued from inside a commit, which is where these cleanups run), so React later removed a node that was already gone and the error escaped out of the next flush; the host is now left to React and the unmount is flushed instead (`unmountPluginRoot`). (2) The page bridge's "a frame joined / left" notifications carried no `url`/`title` and the client read the missing fields as empty, so a second frame showing the same app blanked the first one's title; the bridge now always reports what it knows about the target and the client only overwrites fields a message actually carries.
  - **Tests** — `smoke.mjs` covers the reference sanitizer, the global-name convention (including the real `dsh-plugin-tpt-chronicle` → `__DSH_TPT_CHRONICLE__` lookup and the whole-id fallback), the picker, item creation/resize/bare, revision monotonicity, both op shapes, the apply summary, the prompt, and the main-conversation route (named target, canvas created by name, active-canvas default, notice text, "no canvas block changes nothing"); `bridge/smoke.mjs` asserts every notification about a target carries its url and title; `npm run verify:embed` drives the whole path in Chromium over the DevTools protocol — a fake boot manifest and a local demo bundle that publishes `__DSH_DEMO__.mountEmbedded` — and asserts the picker chip mounts it (`entry="__DSH_DEMO__"`), the plugin's own React render produced the DOM, one bundle load served the second item, `rebuild` re-materialized the bundle (`loads=2`, new stamp) with the badge reading 已挂载, the main-conversation block applied to the canvas it named with the notice opening it, and no teardown error while that canvas swap unmounts hosted plugin items.
- **画布可以承载任何插件，不局限于卡片与控件**：现在通过对话（或画布栏的 `🧩 插件` 选择器）可以把**另一个插件的原生界面**放到画布上。它不是一种卡片类型：插件的客户端包从启动清单里取出并加载，它的嵌入入口挂载到该项自有的宿主节点，此后这个项就和画布上其它东西一样（拖动、缩放、`✎` / `💬` / `⛶` / `⧉` / `📥` / `🗑`，`▢` 切换裸控件外观）。新增两个 `[canvas]` 操作：`addPlugin`（`id` / `title` / `height` / `bare` / `x` / `y`）与 `rebuild`（重建某个已有插件项），两者都会校验（`sanitizePluginRef`）并像其它操作一样汇报（`新增插件 1 · 重建插件 1`），不可用的引用计入 skipped；画布提示词会列出启动清单里的插件（已成功挂载过的标 ✓）并教这两个操作，因此"把工作时序插件放到画布上"在两个对话框里都能直接生效。`applyCanvasSpec` 同时接受解析后的 op 形状与原始形状（`id` / `pluginId` / 字符串 `plugin`），方便程序化调用。嵌入约定：插件发布 `globalThis.__DSH_<去掉 dsh-plugin- 的 ID>__.mountEmbedded(host, api)`（与内置「工作时序」卡一直在用的约定一致：`dsh-plugin-tpt-chronicle` → `__DSH_TPT_CHRONICLE__`），`api` 提供 `render`（独立的 React root）、`dark` 与 `onStatus`，后者显示在插件项的实时徽标上（待挂载 / 加载中… / 已挂载 / 未挂载）；`mount(host, api)` 与纯函数形式也接受，项还可以显式指定入口名。**一次加载、多处挂载**：客户端包每会话只取一次，同一插件的每个项各挂各的宿主（不用 iframe、不引入第二份 React，插件保留自己的 DOM、样式与接口访问）；项头部的 `⟳`（或 `rebuild` 操作）换一个新修订号，从而重新加载客户端包并重新挂载——修订号现在保证严格递增（`nextPluginRevision`），同一毫秒内连续重建不会再留下旧界面。加载失败、没有嵌入入口、id 不在启动清单里时，会显示写明期望全局名与一行示例的说明面板而不是空白框；`🧩 插件` 选择器还会列出插件管理端口报告的动态插件（`◇` 行，它们没有自己的客户端包地址）。**主对话同样可以**：对话行监听器现在也会应用任何回复里的 `[canvas]` 块（与它一直在做的 `[taskcard]` 建卡同一条路径），作用于块里指名的画布（`"canvas": "名字或 id"`，不存在就创建）或当前画布，并在任务台上显示可点击的提示——`画布「发布画布」已应用：新增插件 1`——点它直接打开那块画布；一条回复可以同时带两种协议，画布块先应用。**测试中顺带修掉**两个只在"平面上有插件项/内嵌应用时切换画布"才暴露的拆除问题：其一，插件宿主被 `root.unmount()` 之后又手动清空宿主节点，而 `root.unmount()` 的 DOM 删除会被推迟（React 会推迟在提交阶段内发起的 `flushSync`，而这些清理正是在提交阶段跑的），于是 React 之后去删一个已经不存在的节点、错误从下一次 flush 里抛出来；现在宿主交给 React，卸载本身用 `unmountPluginRoot` 冲刷。其二，网页桥接的"有框架加入 / 离开"通知不带 `url` / `title`，客户端把缺失字段当成空值，导致同一应用的第二个框架把第一个的标题抹掉；现在桥接始终带上已知信息，客户端只覆盖消息里真正携带的字段。测试：`smoke.mjs` 覆盖引用校验、全局名约定（含真实的 `dsh-plugin-tpt-chronicle` → `__DSH_TPT_CHRONICLE__` 查找与整 id 兜底）、选择器、项创建/尺寸/裸控件、修订号单调、两种 op 形状、应用汇报、提示词，以及主对话路径（块里的画布名、按名创建、默认作用于当前画布、提示文本与"无画布块时什么都不变"）；`bridge/smoke.mjs` 断言关于某个 target 的通知始终携带 url 与标题；`npm run verify:embed` 在 Chromium 里用 DevTools 协议跑通全链路（伪造启动清单 + 本地演示包发布 - **The canvas chat can add controls, not just reference them / 画布对话可以新增控件** — on a card's own canvas (`⛶ 最大化` → 副本画布) the chat was only reliable for *editing what was already there*: a control it created with `add` stayed a plane-only item and vanished from the board card on the way back. Now every free item on an instance canvas is **adopted** onto the card it mirrors: `canvasAdoptItems(canvasId)` gives the item's control a stable `bid`, binds the item to it (`from: { card, bid }`) and publishes the control onto the card, so the plane and the card agree. Adoption runs right after the chat applies its `[canvas]` spec, and again from the canvas widget's apply hook (which also covers the quick editor and the manual `+ 控件` button). The controls land in one column below what is already on the plane, and the card's control order keeps following the plane's arrangement — mixed in with the existing items, not appended blindly.
  - The canvas prompt now states that this plane is a card's copy and that `add` / `addCard` are the way to bring in whatever is missing ("缺什么就直接加，不必先问用户"), and the empty-chat hint says new controls are hooked back onto the card.
  - Normal canvases are untouched (`instanceCardOf` returns `""`), items already bound to the card are left alone, and a multi-control item stays a plane-only card because one canvas item maps exactly one control. Adoption is idempotent.
  - **Fixed while testing this**: `applyCanvasSpec` read `op.block.kind` unguarded, so a malformed `add` op (one the parser would have dropped) crashed the whole canvas drawer. Both `add` and `addCard` now skip malformed ops and count them as skipped, exactly like an unknown item id.
- **画布对话可以新增控件**：在卡片自己的画布（`⛶ 最大化` → 副本画布）上，对话原先只对**改已有控件**可靠——它用 `add` 新建的控件只留在画布上，返回任务台时随平面一起消失。现在实例画布上的自由项会被**收养**到它对应的卡片：`canvasAdoptItems(canvasId)` 给该项的控件分配稳定的 `bid`、把项绑定到它（`from: { card, bid }`）并把控件写回卡片，于是画布与卡片始终一致。收养在对话应用 `[canvas]` 之后立即执行，也会从画布控件的应用钩子再跑一次（因此快速编辑器、手动 `+ 控件` 也覆盖）。新控件按一列排在已有项下方，卡片的控件顺序继续跟随画布排布——是**混进**现有顺序，而不是简单追加。画布提示词现在会说明这是某张卡片的副本画布、缺什么就用 `add` / `addCard` 直接加（"缺什么就直接加，不必先问用户"），空对话提示也会说明新加的东西会挂回卡片。普通画布不受影响（`instanceCardOf` 返回 `""`），已绑定到该卡片的项不动，多控件项仍只留在画布上（一个画布项正好对应一个控件），收养可重复执行而无副作用。**测试中顺带修掉**：`applyCanvasSpec` 的 `add` 分支直接读 `op.block.kind`，一个畸形 op（本该被解析器丢弃）会把整个画布抽屉打崩；现在 `add` 与 `addCard` 都会跳过畸形 op 并计入 skipped，与"引用了不存在的 id"同一种处理。

- **Preset card: 工作时序 / 预设卡「工作时序」** — the board ships a sixth built-in card that hosts the **dsh-plugin-tpt-chronicle** panel (装置对象 / 工作脉络 / 材料证据 / 使用足迹, with its own 同步数据 action). Unlike the other built-in cards this one renders *another plugin's* UI:
  - The card asks the TPT client bundle to mount itself into a node the card owns (`mountEmbedded(node, { render, dark, onStatus })`), so the panel keeps its own DOM, its own stylesheet and its own `/tpt-chronicle/api/*` access. No iframe, no second React copy, and every panel button (including the prompt-sending 复盘 actions) keeps working.
  - The bundle is loaded once per page from its own revisioned boot row (`window.__DSH_BOOT__.entries`), never twice, and the card degrades to an explicit install hint when the plugin is absent (`dsh plugin --profile web add …`).
  - The card is a normal built-in card otherwise: draggable, resizable (384×330 default), `⛶` fullscreen (where the panel's side nav appears), `▴/▾` collapse, `×` hide, `复位卡片` reset, and its layout persists in `localStorage` like every other card.
  - The board's dark theme reaches the panel (`data-embed-dark="1"` on the host re-skins the panel's surfaces without touching its geometry), and the card header badge shows the indexed material count reported by the panel on each load.
- **预设卡「工作时序」**：工作台新增第六张内置卡，用来承载 **dsh-plugin-tpt-chronicle** 的面板（装置对象 / 工作脉络 / 材料证据 / 使用足迹，含它自己的「↻ 同步数据」）。与其它内置卡不同，这张卡渲染的是**另一个插件**的界面：卡片让 TPT 客户端包把面板挂载到自己持有的节点上（`mountEmbedded(node, { render, dark, onStatus })`），因此面板保留自己的 DOM、样式表和 `/tpt-chronicle/api/*` 访问能力——不用 iframe、不引入第二份 React，面板里所有按钮（含需要向会话发消息的复盘动作）都能用。客户端包每页只按自己的启动清单行（`window.__DSH_BOOT__.entries`）加载一次，插件缺失时卡片显示明确的安装提示（`dsh plugin --profile web add …`）。其它行为与普通内置卡一致：可拖拽、可缩放（默认 384×330）、`⛶` 全屏（此时显示面板侧栏导航）、`▴/▾` 收起、`×` 隐藏、`复位卡片` 复位，布局照常存入 `localStorage`；工作台暗色主题会传导到面板（宿主上的 `data-embed-dark="1"`，只改面板表面色、不动它的排版），卡片头部徽标显示面板每次加载后上报的材料份数。

## v0.23.0

- **The agent can operate an embedded web page / 让 agent 操作内嵌网页**: an embedded app can now be marked **受控** (controlled), and the workbench — and therefore the agent — can really click, type, scroll and read inside it. The missing piece was architectural: a cross-origin iframe is opaque to its parent, so no amount of client code could act on it. The repo now ships a **local page bridge** (`bridge/server.mjs`, zero dependencies) that closes the gap:
  - `GET /p?url=…&target=…` proxies the target page and **injects an agent script** into it; that script opens a WebSocket back to the bridge and executes commands *inside the page* (its own origin), so the plugin never needs script access it should not have.
  - Commands: `read` (title, body text, and the visible form fields), `query`, `click` (by CSS selector **or by button text**), `type` (+ `submit`), `press`, `select`, `check`, `scroll`, `wait`, `eval`, `back`, `forward`, `reload` — each returning a JSON result, with per-command timeouts and `no-page`/`timeout` answers instead of hangs.
  - **Agent loop**: the card and canvas prompts now list the controlled apps and teach a `[page]` block — `[page] { "actions": [ … ], "then": "…" } [/page]` — which the workbench executes after applying the reply, reports in the chat log (`读取内容 ✓ 「标题」…；点击 #buy ✓ 「购买」`), and optionally hands back to the agent through `then` for a second round. Page actions can be mixed with `[taskcard]`/`[canvas]` blocks in the same reply.
  - **Workbench UI**: `🌉 桥接` in the board header holds the bridge URL / token / the `允许 agent 操作网页` switch (the safety gate, off by default) plus a connection test; every controlled app shows a live badge (`受控 · 已连接` / `桥接离线` / `未连上`), and the card editor has the `受控` checkbox next to `填满`.
  - **Several frames, one page**: a target keeps every live frame socket (a board card plus its canvas copy plus a fullscreen overlay can all show the same app); a command is broadcast to all of them and the first answer wins — this also fixed a connection war where each new frame evicted the previous one.
  - **Safety**: the bridge is loopback-only by default, supports a bearer `--token`, an `--allow` host allow-list and a response size cap; the `允许 agent 操作网页` switch gates execution, and nothing runs unless a page is embedded with `受控` on. It is a local tool: whatever the page itself can do, the bridge can do inside that page.
- **Tests**: `bridge/smoke.mjs` (`npm run test:bridge`) covers the proxy (injection, framing headers dropped, non-HTML passthrough, token gate, URL validation, allow-list) and the WebSocket hub (page registration, host→page routing, results, `no-page`, timeout, multi-frame targets, disconnect broadcast). `smoke.mjs` covers the client protocol (target keys, settings sanitize, proxied URL, `[page]` parsing/validation, action summaries, the controlled-app picker, the badge markup, the editor switch, the enable gate, the bridge panel and the prompt teaching). `npm run verify:embed` now drives the **real** path in Chromium over the DevTools protocol (real time, no virtual clock): it embeds a controlled app, waits for the injected agent, runs a `[page]` action list — two clicks and two reads — and asserts the page itself reports `点击 2 次`, with the badge reading `受控 · 已连接`.
- **让 agent 操作内嵌网页**：内嵌应用现在可以勾选 **受控**，工作台与 agent 就能真的在里面点击 / 输入 / 滚动 / 读取。原先做不到的根因是架构性的——跨源 iframe 对父页面不透明，客户端怎么写都动不了它。仓库因此新增**本机页面桥接**（`bridge/server.mjs`，零依赖）：`/p` 代理目标网页并**注入受控脚本**，脚本用 WebSocket 连回桥接、在页面自己的源里执行命令，插件不需要任何越权脚本能力。可用动作：`read`（标题 / 正文 / 可见输入框）、`query`、`click`（CSS 选择器**或按钮文字**）、`type`（可 `submit`）、`press`、`select`、`check`、`scroll`、`wait`、`eval`、`back`/`forward`/`reload`，每条都返回 JSON，并有超时与 `no-page` 兜底。对话侧新增 `[page]` 协议：卡片与画布提示词会列出受控应用并教 agent 输出 `[page] { "actions": [ … ], "then": "…" } [/page]`，执行后在对话记录里汇报（如 `读取内容 ✓ …；点击 #buy ✓ 「购买」`），并用 `then` 把观察结果回灌给 agent 继续下一轮；可与 `[taskcard]` / `[canvas]` 同回复混用。工作台头部新增 `🌉 桥接` 面板（地址 / 令牌 / **允许 agent 操作网页** 开关，默认关闭，作为安全闸门）与连通性测试，受控应用上有实时徽章，卡片编辑器里 `受控` 就在 `填满` 旁边。另修复：同一页面在多个框架（卡片 + 画布副本 + 全屏）同时显示时新框架会驱逐旧框架造成连接风暴——现在同一 target 保留所有活跃框架，命令广播、先答者胜。安全上：桥接默认只监听回环、支持 `--token` 与 `--allow` 主机白名单、限制响应体大小，且必须页面勾选 `受控` + 面板打开开关才会执行。

- Refactor pipeline hardened: the temporary helper is now a **blank session** created through `sessions.create` in the source session's workspace (neither history nor agent inbox inherited); `session.fork` remains the fallback, and that path clears inherited queue items / cancels a stale open turn before prompting. The helper is opened for its event window and the reply is read from `assistant/message` events plus streaming deltas, accepted only after the instruction has landed as a user message — otherwise the popup degrades to the main session instead of idling.
- Repository tidy: README control/style catalogs aligned with the implementation, a release changelog and an `npm run check` syntax script for the shipped bundle.
- 控件目录扩展 `table` / `code` / `toggle` / `countdown` / `bars`；临时 helper 改为 `sessions.create` 空白会话（fork 兜底并清理遗留队列/回合），回复从事件窗口读取；补齐变更记录与 `npm run check`。

## v0.7.0

- The card `💬` conversation now **calls a temporary agent session** (`sessions.fork` + `session.prompt`) instead of posting into the main conversation: the popup streams the helper agent's reply, applies its `[taskcard]` block directly, and archives the helper with `workspace.archiveSession`.
- Graceful fallback to the main-session channel when the agent services are unavailable.
- 卡片 `💬` 对话改为调用临时 agent 会话（fork + prompt），弹窗流式回显并直接应用 `[taskcard]`，结束后归档；不可用时回退主会话。

## v0.6.0

- New `trend` control: sparkline-style line + area chart (2–48 points), tinted by the card accent color.
- 新增 `trend` 趋势图控件，随卡片强调色着色。

- 新建卡片改为「先建草稿 + 自动弹右上角对话」；新增卡片整体样式 `style` 白名单。

## v0.3.0

- Card content became a declarative control list: `text` / `heading` / `note` / `stats` / `progress` / `kv` / `links` / `chips` / `checklist` / `counter` / `button`.
- Interactive widget state (checked items, counters) persists per card and per stable `key`.
- `fill` button action writes text into the main composer for review before sending.
- Unknown control kinds keep their original fields and upgrade automatically once supported.
- 卡片内容升级为控件目录；交互状态持久化；未知控件保留原始字段并可自动升级还原。

- 自定义悬浮卡片与 `[taskcard]` 卡片协议。
